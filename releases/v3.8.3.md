# v3.8.3 — 面向 Agent 的资源市场（4/10）：撮合编排器（订单状态机 ↔ 容量 hold/release ↔ 计量 open/record 联动，一次 hold 恰好一次 release）

## 一、交付了什么

v3.8.0 给了撮合入场纯函数 `match_offer_ask`（形态/单位/限价/数量校验，建单即
`Matched`），v3.8.1 给了注册容量账本（register/hold/release），v3.8.2 给了计量账本
（open/record/结算视图）。但三者此前**互不接线**：成交后不会真的预留供给方容量，取消/
结算也不归还，执行期更不会自动开计量线。v3.8.3 新增**纯确定性、内存态的撮合编排器
`MatchingEngine`**，把订单状态机的每一条边与容量账、计量账按确定性规则联动起来。零浮点、
零 syscall、零 unsafe、无 panic 路径，数量/金额全部 `u128` checked 运算。

新增文件 `gsn-core/src/economy/resource/matching.rs`，编排面持有订单集（有序 Vec）、
`CapacityRegistry`、`MeteringLedger`，提供按状态边驱动的方法：

1. **挂单容量闸门 + 成交提交**
   - `submit(offer, ask)` 先调 `capacity.check_offer`（供给方必须已注册同形态/同维度容量、
     挂单量 ≤ 当前可售，fail-closed），再用 `match_offer_ask` 建单（`Matched`）；订单 id
     由引擎分配 `ord-{n}`（单调不重用）。`submit_named` 使用显式 id，重复 id 报
     `RESOURCE_DUPLICATE_ORDER`。未知订单的任何编排操作统一报 `RESOURCE_ORDER_NOT_FOUND`。
   - 提交**不**预留容量——预留只发生在下一条边。
2. **容量预留与归还（一次 hold 恰好一次 release）**
   - `hold_capacity`：仅 `Matched → CapacityHeld`，对供给方按成交量 `filled_quantity`
     hold；hold 超量由容量账本 fail-closed 拒绝，且**订单停在 Matched、容量账不改写**。
   - `begin_execution`：`CapacityHeld → Executing`。
   - `settle`（`QaPending → Settled`）、`adjudicate_settle`（`Disputed → Settled`）、
     `adjudicate_slash`（`Disputed → Slashed`）：进入终态前 release 成交量；判罚同样归还
     撮合预留容量（资金罚没在 v3.8.4/3.8.5，本版只归还容量）。
   - `cancel`：`Matched` 取消时尚未 hold，**不**释放；`CapacityHeld` 取消时 release
     成交量；执行期及以后由状态机拒绝取消。
3. **计量随订单状态联动**
   - `begin_metering`：仅 `Executing → Metering`，自动为订单开计量线
     （`allocated = filled_quantity`、`unit_price = fill_unit_price_micro`）；开线失败
     具名拒绝且订单停在 Executing。
   - `report_usage(amount)`：仅 `Metering` 态允许，底层 append-only 正计量、
     `consumed ≤ allocated` fail-closed，超配额失败不改写。
   - `to_qa`：`Metering → QaPending`；`dispute`：`QaPending → Disputed`（争议期间容量
     继续持有，不释放）。
4. **跨账守恒不变量 `invariant_holds`**
   - 除容量账本（`held ≤ capacity`）与计量账本（`reserved = consumed_cost + refund`）
     各自不变量外，新增**跨账守恒**：每条注册的 `held` 恰好等于「已 hold 且未进入终态」
     同键 `(provider, kind, unit)` 订单的成交量之和（checked 求和）。这把"一次 hold
     恰好一次 release"从口头约定变成可单测断言。
5. **失败不改写（fail-closed 补偿）**：每条边都先执行可能失败的记账动作（hold/open/
   release/record），成功后才推进订单状态；底层账本在出错路径自身不改写，故一旦某条边被
   具名拒绝，订单停在原态、容量与计量两账都不被污染，可安全重试或改道取消。
6. **2 个新具名错误 + 状态诚实位更新**：`ResourceError` 新增 `OrderNotFound /
   DuplicateOrder` 并补齐 `RESOURCE_*` Display；PMB `resource_market_status` 诚实位置
   `enforceable.matching_orchestration=true`、`provided.matching_engine_persistence=false`，
   escrow/stake/onchain 仍为 false。

## 二、测试（旧实现无法表达的断言，8 新增）

`economy/resource/matching.rs` 8 个，全部针对"三张账此前互不接线、无法保证 hold/release
与计量随状态联动"：

1. `happy_path_holds_meters_releases_and_conserves`：全前向链路 Matched→…→Settled，
   可售 1000→700（hold 300）→结算后恢复 1000；计量 allocated=300/consumed=290/
   refund=20；跨账不变量成立。
2. `hold_is_failclosed_when_peer_consumes_capacity_first`：两单同在容量尚满时提交，
   A 先 hold 950 仅剩 50，B 再 hold 100 超量被拒且订单仍 Matched、容量不改写；B 改道
   Matched 取消不释放。
3. `cancel_at_matched_no_release_and_at_capacity_held_releases`：Matched 取消容量不变；
   CapacityHeld 取消释放归还；进入 Executing 后状态机拒绝取消。
4. `metering_opens_only_in_metering_and_usage_is_bounded`：执行期未开线时 report_usage
   被状态机拒绝；超预留（allocated=100 记 120）fail-closed 不改写；恰好到顶允许。
5. `dispute_slash_and_settle_both_release_capacity`：争议期间容量继续持有（仍 700），
   仲裁 Slash 与仲裁 Settle 两条分支都在进终态时归还容量。
6. `submit_enforces_listing_gate_and_unique_ids`：无注册容量挂单 fail-closed；挂单量超
   注册可售拒绝；同 id 重复提交 `DUPLICATE_ORDER`。
7. `unknown_order_operations_named_not_found`：对未知订单 order/hold_capacity/settle
   统一 `ORDER_NOT_FOUND`。
8. `released_capacity_is_reusable_by_next_order`：容量被首单占满期间新挂单过不了闸门，
   首单结算全量归还后第二单可重新吃满容量（hold/release 真正闭环可复用）。

## 三、诚实边界

- 撮合编排器是**确定性内存编排面**：不持久化、不跨进程/跨节点共享、不是全局单例；宿主或
  T1 市场门面持有它并在受理真实挂单/状态推进时调用。网络撮合、跨区域供给发现、P2P 订单
  传播不在本版。
- 本版**只编排容量预留与计量开线/上报**，**不托管资金、不分账、不质押、不罚没资金、不
  接真实支付/链**：资金守恒分账在 v3.8.5，质押冻结/罚没在 v3.8.4，BTC/ETH/稳定币结算与
  私钥隔离在 v3.9.x。`adjudicate_slash` 只归还撮合预留容量，罚没金额需等质押账本落地。
- `submit` 的容量闸门校验的是"挂单量 ≤ 当时可售"，多单可能同在容量充足时成交而在
  `hold_capacity` 阶段竞争——超卖方在 hold 边被 fail-closed 拒绝并停在 Matched，可改道
  取消或等待容量归还；本版不做自动排队/抢占/重排（调度优先级在后续版本）。
- 不新增能力令牌、**不经 PMB 受理外部写单**：`resource_market_status` 仍为只读，
  编排方法目前只在库内可调用/可单测；面向插件/进程的挂单受理门面（T1 official）在后续
  小版本接入，未接线的写方法继续不注册（NotFound），不伪造可用。
- 外部数字（90% 沙盒 CPU<5%、超卖 50×、镜像访问 4.2–13.3% 等）仍为第三方报道、非本仓
  复测，仅作机制动机，不写进代码或作为已验证结论。
