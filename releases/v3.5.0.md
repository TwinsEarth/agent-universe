# v3.5.0 — B2：进程插件 outbox 主动通信（新能力）

v3.5.0 是 v3.4.5 之后的**中版本（minor）**。本版核心是 v3.4.2 审计 §4 判定为 minor 的
**B2 —— 进程插件 outbox 主动通信**：让一次性、无状态的进程插件（Python）在一次 entry 调用内
**主动发起** PMB 通信（点对点 `send_to` / 广播 `publish`），而不只是被动返回结果。
至此，v3.4.2 审计标注的 B1/B2/B3 三项核心架构性 gap 已全部落地（B1/B3 在 v3.4.5，B2 在本版）。

## 一、接地核实：进程插件是一次性、无状态的 Python 调用

设计前先接地核实进程插件的真实形态（`runtime/process.rs` + `sandbox/runtime/process.rs`）：

- 进程插件的每次 entry 调用都经 `ProcessSandbox::run_code` 起一个**新解释器**：把 bootstrap
  写到隔离工作目录的 `main.py`，再执行 `python3 main.py`（Windows 用 `python`）。
- `current_dir` 为隔离工作目录，`sys.path[0]` 即该目录，故 `import plugin` / `import host`
  都能在同目录找到模块。
- 进程在调用结束后即退出：**无法持有持久连接、不能直接访问 host、不能直接触达 PMB**。

因此「让进程插件主动通信」不能靠给它一根常驻 socket（违背一次性 + 隔离前提），需要一个
不开放网络、由宿主回收并代投的机制 —— 即 outbox。

## 二、B2 outbox 设计（核心）

**插件侧（`host.py`）**：spawn 带 entry 的进程插件时，额外向隔离工作目录写入 `host.py`，
暴露两个函数（`import host` 后调用）：

- `host.send_to(target, payload, capability="plugin:message:send")`：声明一条点对点消息。
- `host.publish(payload, capability="plugin:message:send")`：声明一条广播事件。

这两个函数**不开任何网络连接**，只把消息逐行 append 到工作目录的 `outbox.jsonl`
（JSON Lines，字段 `kind` / `target` / `capability` / `payload`，`json.dumps(ensure_ascii=False)`）。

**宿主侧（回收 + 代投）**：

1. `invoke_entry` 在子进程 exit 0 后调 `collect_outbox()`：读回 `outbox.jsonl`，逐行解析为
   `OutboxMessage`，存入实例字段 `outbox`，随后清空文件（避免重复读）。
2. `PluginHost::call` 在实例借用块内同时取走方法返回值 `bytes` 与 `drain_outbox()` 的 outbox；
   drop 借用后**代表插件**逐条投递 PMB：`send` → `self.send_to(...)`、`publish` →
   `self.publish(...)`，最后返回方法返回值。

数据流：

```text
plugin.py  ──host.send_to/publish──►  outbox.jsonl（不开网络）
                                          │ 子进程退出后宿主读回
                                          ▼
                          ProcessInstance.outbox（Vec<OutboxMessage>）
                                          │ host.call 取出
                                          ▼
              宿主代表插件经 PMB send_to / publish（唯一投递点，七道检查）
```

## 三、安全边界：宿主仍是唯一 PMB 投递点

outbox 只让插件「**声明意图**」，不授予它任何 PMB 投递能力。真正的投递仍由宿主在
`dispatch_for_plugin` 内完成（构造消息 → `bus.sign_message` → `bus.dispatch`），
完整经过 PMB 既有检查（`bus.rs validate_sender` + 路由）：

1. **大小**：`check_size`；
2. **发送方状态**：已注册且 `RUNNING`；
3. **能力令牌**：存在且 `plugin_id` 与 source 一致（防伪造 source）；
4. **能力已知且被授予**：`capability` 可解析且令牌 `has(cap)`；
5. **速率**：发送方速率配额；
6. **签名**：用发送方会话密钥重算 HMAC，常时比较（任何字段/密钥被篡改即失败）；
7. **nonce 防重放**：同一 nonce 只接受一次；
   路由时再校验**目标 `RUNNING` 且未隔离**（广播收集所有 RUNNING 插件，除发送方）。

插件进程本身不持有会话密钥、不接触 PMB 句柄，因此无法绕过上述检查自行投递或伪造来源。

## 四、capability 规范：必须用总线已注册的能力名

PMB 总线只认 `group:resource:action` 形式的规范能力名（`bus.rs` 对未知名 reject
「未知能力名 {capability}」）。`host.py` 的两个函数默认能力均为基础能力
`plugin:message:send`（全级别拥有）。插件若显式传 `capability`，必须：

- 是总线已注册的已知能力名（见 `capability.rs Capability::ALL`）；
- 且已被该插件的能力令牌授予，否则在投递时被拒。

**不存在** `"message"` / `"event"` 这类裸能力名（这是本轮端到端测试首次跑出的问题，见下）。
`collect_outbox` 对缺失 capability 的行同样回退到 `plugin:message:send`。

## 五、spawn_concrete 重构（可测试性）

原 trait `spawn` 直接返回 `Box<dyn PluginInstance>`，导致 process.rs 测试无法访问具体字段
（`ProcessInstance.sb` 在 trait object 上 E0609）。重构为：

- trait impl 的 `spawn` 改为 `Ok(Box::new(self.spawn_concrete(manifest)?))`；
- `impl ProcessRuntime` 新增独立 inherent 方法 `pub fn spawn_concrete(&mut self,
  manifest: &PluginManifest) -> PluginResult<ProcessInstance>`，承载完整 spawn 逻辑
  （supports 校验、`ResourceLimits` 映射、waivers 经 `map_waiver`、`SandboxConfig`、
  沙箱 create/start、写 entry 与 `host.py`、登记实例、返回具体类型）。

测试用 `spawn_concrete` 取得具体 `ProcessInstance`，以便在覆盖 entry 时访问沙箱字段。

## 六、新增回归测试（修复前会失败）

5 个新测试（process.rs 3 + host.rs 2）：

- `outbox_captures_plugin_initiated_messages`：插件 entry 内调 `host.send_to` + `host.publish`，
  宿主解析出 2 条消息，断言 kind/target/capability/payload 全部正确。
- `outbox_empty_when_plugin_does_not_communicate`：插件不写 outbox 时，drain 为空、调用正常。
- `outbox_send_without_target_rejected`：`send` 缺 target 被 `collect_outbox` 拒绝。
- `call_delivers_plugin_send_outbox_over_pmb`：宿主 `call` 后，目标收件箱收到由宿主代投的
  已认证消息（断言 source/target/payload/signature/nonce）。
- `call_delivers_plugin_publish_outbox_over_pmb`：`call` 后两个收件箱均收到广播。

按铁律，这些端到端测试在修复前会失败：首次运行即因 host.py 默认 capability 为裸
`"message"` 而报 `Bus("未知能力名 message")`，修正为 `plugin:message:send` 后才通过。

## 八、版本语义说明

v3.4.2 审计版本语义规定「大版本=架构重构、中版本=新功能插件化、小版本=只更新独立插件」。
B2 被判定为 **minor（新能力，不改内核、不破坏既有插件）**，与本次发布 **v3.5.0（minor）**
一致，**无版本语义偏离**。B1/B3 在 v3.4.5（patch）推进的偏离说明仍见 `releases/v3.4.5.md`
第五节，本版不重复。

## 九、诚实边界与后续

- outbox 只在「插件被调用（call）」的窗口内回收：插件在非调用期不会运行，也无法主动唤醒
  （进程插件一次性、无后台常驻）。需要事件驱动/长驻能力属后续架构方向。
- 消息签名为对称 HMAC（提供防篡改/防伪造，不提供非对称来源证明）；
  chain-anchor/bridge 为离线构造、无 RPC。
- B2 不改变隔离边界：`host.py` 不开网络，沙箱仍按既有策略限制 egress / 文件系统。

## 十、结论

v3.5.0 让进程插件从「**被动返回结果**」走向「**主动发起通信**」：插件在一次 entry 调用内
即可经 outbox 声明点对点消息与广播，宿主回收后通过 PMB 代投，且不放松任何既有检查。
B1/B2/B3 三项核心架构性 gap 至此全部闭环。
