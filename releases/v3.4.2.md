# v3.4.2 — 全局审核版本：补齐插件生命周期/信任/黑名单接线 + 架构合规关卡

v3.4.2 是 v3.4.0（9/9 官方插件业务化里程碑）之后的**小版本（patch）**。按版本语义，
patch 只更新独立插件或对外接线，**不改内核架构、不影响其他插件**。

本版做一件事：**重新审视 v3.0.0 大版本及其下全部中/小版本的每一处代码与功能，判定是否
彻底贯彻「一切插件化」**，并修复审计发现的 4 处「内核能力已实现但未接对外路由/检查」的
patch 级 gap。

完整审计见 [`docs/AUDIT-v3.4.2-plugin-architecture.md`](../docs/AUDIT-v3.4.2-plugin-architecture.md)。

## 一、审计范围与方法

- 审计对象：`gsn-core/src/plugin/` 16 文件 / 约 6,077 行 + 9 个官方插件 entry。
- 方法：逐文件通读 + 调用点 grep + 全量测试。
- 两条自定规则：**「没有调用点的修复不算修复」**、**「在修复前代码上能通过的测试什么也没证明」**。

## 二、审计结论：内核与插件层已彻底贯彻（10 项）

1. 内核五子系统完整（registry/bus/arbiter/blacklist/lifecycle）。
2. 五级分类由 name 前缀判定（tier.rs）。
3. 仲裁器四重校验真实（摘要重算、Ed25519 签名、官方副签须在受信 roots、T3 须显式信任且 fail-closed）。
4. 能力矩阵真实（T0 Granted、T1/T2 Declarable、T3 永远 Denied、内核能力仅 T0）。
5. 隔离运行时诚实声明（native 不隔离、process 真实进程、wasm 类型化拒绝）。
6. process 后端能力声明按平台诚实（Windows 额外 Job Object 三能力）。
7. invoke_entry 防注入（方法名合法、payload 经 json.loads、getattr 安全调用）。
8. 黑名单生命周期完整（精确匹配、申诉不解封、解封须新模块摘要）。
9. 热更新/热插拔/热兼容完整（install/uninstall/hot_reload/stop/start/load_legacy/check_abi）。
10. 9 个官方插件全部业务化（official_entry_source 9/9 Some）。

## 三、A 类 patch 级 gap 修复（4 项，均在 handle_plugin_api）

| ID | 严重度 | 修复 |
|---|---|---|
| G1 | 高 | 新增 `POST /plugins/{id}/stop`、`/start`（暂停/恢复但不卸载的热插拔中间态） |
| G2 | 高 | 新增 `POST /plugins/trust`（信任第三方发布者，补齐 T3 安装前置） |
| G3 | 高 | 新增 `GET /plugins/blacklist`（黑名单查询）、`POST /plugins/{id}/unblock`（解封） |
| G4 | 中 | entry_source 合规关卡升级为自动遍历 official_ids()（未来漏配 entry 即失败） |

路由细节：`GET /plugins/blacklist` 必须放在通用 `GET /plugins/{id}` 详情路由之前，否则
path "blacklist" 被当作 id。所有新增 POST 管理路由都在 `rest_authorize` 之后处理，受
fail-closed 认证保护。

## 四、新增回归测试（修复前会失败）

- `plugin_api_stop_start_routes_reachable`：Running → stop → Stopped → start → Running。
- `plugin_api_trust_route_fail_closed`：缺 key→400、提供 key→200。
- `plugin_api_blacklist_query_and_unblock`：add→GET 1 条→相同摘要 400→缺字段 400→不同摘要 200→清空。
- `entry_source_for_business_plugins`：自动遍历 9 个官方插件，断言 entry 为 Some 且字段非空。

## 五、B 类架构性 gap：v4.0.0 major 路线（不在 patch 实施）

- **B1**：主业务数据面仍是单体（主 REST 路由仍调用单体 market，9 官方插件是并行承载而非接管）。
- **B2**：PMB 插件间通信在 daemon 业务中零调用（进程插件无 host function、无法主动通信）。
- **B3**：4 个 T0 系统插件仅 identity 真承载业务（net/storage/chain 只注册 status）。

## 六、验证

- 新增 4 个可达性/合规测试：全部通过（修复前会失败）。
- 全量 `cargo test`：0 failed；`clippy -D warnings`：0 warning；`fmt --check`：通过。
- check-no-panics / check-unsafe-containment / check-version：通过。

## 七、已知未修项（诚实边界）

- node.rs/api.rs 约 8 处 `let _ = node.persist()` 丢弃持久化错误。
- API token 无法表达标准 DID；结算仍按托管总额付款而非中标价。
- 消息签名为对称 HMAC（跨节点非对称签名留待后续）；chain-anchor/bridge 为离线构造。
- B1/B2/B3 留待 v4.0.0 major。

## 八、结论

v3.0.0 → v3.4.0 在**内核与插件层面已彻底贯彻「一切插件化」**；v3.4.2 补齐了 4 处已实现
内核能力的对外接线并新增合规关卡。v4.0.0 的目标是让插件从「并行承载」走向「接管主数据面」。
