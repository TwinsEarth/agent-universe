# v2.8.6 — MCP 校验接入生产传输（sse/stdio）/金额入口拒绝浮点/规范签名载荷整数化

对应《v2.8.2 增量审计 / Gap Analysis》**§3.5（MCP 部分）/ §4.1（部分修复，等于未修）**。
v2.8.2 的 MCP 数据面与跨语言签名存在两类问题：

1. **参数校验写了、测了，但不在任何生产路径上**：`validate_arguments`
   （`tool.rs`）能做必填与类型校验，却只被零生产调用的 `McpServer::handle_tools_call`
   （`server.rs`）调用；两个真实传输——HTTP 的 `sse.rs` 与 Claude Desktop 的
   `stdio.rs`——在 ToolsCall 分支直接 `bridge.call(name, &args)` 绕过校验。
   于是 `market_deposit {"amount":"lots"}` 经 `get_money` 的
   `as_f64().map(|f| f as i64)` 落空后 `unwrap_or(Money::ZERO)`，**存 0 并返回
   `{"status":"deposited"}`**；`market_arbitrate {guilty:1}` 经 `unwrap_or(false)`
   静默降级。
2. **签名载荷仍含浮点**（§4.1）：金额虽已整数化，但 `aca/receipt.rs` 的
   `ResourceMetering` 仍持有 `bandwidth_mb: f64` / `energy_joules: f64`，主路径用
   `..default()` 把 `0.0` 带进被签名载荷。三端对同一默认值发出不同字节：Rust
   `0.0` / Python `0.0` / JS `0`；而唯一的跨语言固定向量载荷不含小数，CI 看不见。

## 根因

- 存在两套并行的 ToolsCall 实现：零调用的 `McpServer`（有校验）与两个真实传输
  （sse/stdio，无校验）。校验只接在“不会被使用的入口”上，按审计规则“没有调用点的
  修复不算修复”。
- 金额入口用 `as_f64().map(|f| f as i64)` 做宽容转换，把“非法字符串/小数”静默
  变成 0，再叠加 `unwrap_or(ZERO)`，使错误输入得到“成功”响应。
- 规范签名载荷没有在类型层面排除浮点：`f64` 字段可被序列化，且各语言对 `0.0` 的
  表示不同，跨语言逐字节一致在构造上不成立。

## 修复

### 1. 统一查找→校验入口，并接入两个生产传输（§3.5）

- `tool.rs` 新增 `find_tool<'a>(tools, name) -> Option<&'a ToolDefinition>`，
  与 `validate_arguments` 构成单一查找→校验入口。
- **`sse.rs`（生产 HTTP 路径）**：ToolsCall 在未知工具检查后、`bridge.call` 前
  接入 `find_tool → validate_arguments`，校验失败返回
  `McpError::InvalidParams`（JSON-RPC 错误码 **-32602**，HTTP 400），不再进入
  执行器。
- **`stdio.rs`（Claude Desktop 路径）**：用 `match find_tool` 块表达式接入同一
  校验（`Some` 内校验失败返 -32602、通过才执行；`None` 走未知工具
  `isError:true`）。
- 由此“新增一条绕过校验的传输”在结构上做不到：两个真实传输都必须经同一校验入口。

### 2. 金额入口只接受整数，非法即拒绝（§3.5 / §4.1）

- `market_tools.rs` 的 `get_money` 删除 `as_f64().map(|f| f as i64)` 浮点截断，
  只保留 `as_i64()`：`"lots"`、`10.5`、`10.0`（serde_json 中亦为 f64）均不
  再被静默变成 0。
- `api/rest.rs` 的 `AccountDeposit` 同步：JSON body 金额只取 `as_i64()`，URL
  query 为字符串→解析整数；删除浮点截断。
- CLI `bin/gsn.rs` 的 deposit 由 `parse::<f64>` 改 `parse::<i64>`，避免命令行
  传入整数却被序列化为浮点、再被服务端拒绝。

### 3. ACA Receipt 计量整数化，规范载荷无浮点（§4.1）

- `ResourceMetering.bandwidth_mb` / `energy_joules` 由 `f64` 改 **u64**，
  规范签名载荷中以整数序列化（`"bandwidth_mb":100`），从类型层面排除浮点，
  三端逐字节一致。

## 验证

- 新增 `tests/v286_test.rs`（8 测试）：
  1. `amount:"lots"` 被 -32602 拒绝，且不返回 `deposited`（不静默存 0）；
  2. `amount:10.5` 浮点被拒；
  3. `amount:10.0`（整数值 f64）被拒；
  4. 缺失 `amount` 被拒并指名 amount；
  5. `market_arbitrate` 的 `guilty:1`（数字而非 boolean）被拒并指名 guilty；
  6. 正常整数 `amount:250` 成功；
  7. `find_tool` / `validate_arguments` 统一入口（命中/未命中、非法/合法）；
  8. Receipt 规范载荷为整数、不含 `100.0`/`500.0`。
- **测试有效性已实证**（审计规则2“在修复前代码上也能通过的测试什么也没证明”）：
  临时令 `validate_arguments` 返回 `Ok(())`（模拟旧实现无校验），v286 套件
  **6 failed / 2 passed**，恢复后 8 测试全过。
- 同步修正 v235 两处浮点旧用例（`amount:250.0`/`500.0` → 整数）。
- `cargo test --tests`：全量 0 failed；`cargo clippy --all-targets -- -D warnings`
  退出 0。

## 边界说明（不夸大）

- 本次仅整数化 `ResourceMetering`（进签名载荷）；`aca/reputation.rs` 内部
  `MultiReputation` 维度分仍为 f64，但不进入 Manifest/Message/Receipt 签名载荷，
  不影响跨语言签名一致性，留待后续。
- 校验接入的是 sse/stdio 两个真实传输；若未来新增传输，仍须经统一
  find_tool→validate_arguments 入口（已在结构上收口）。
