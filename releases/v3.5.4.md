# v3.5.4 — 重启持久化全字段保真（W-04 任务规格 / W-05 智能体卡片）

v3.5.4 是 v3.5.3 之后的**补丁版本（patch）**，只做缺陷修复，无破坏式重构。本版把 Windows
实机分支（`win-deploy-v3.5.0`，提交 `416b5bc` W-04 / `9603735` W-05）已经实机验证通过的
两个"重启丢字段"修复回合到云开发主线。

## 一、问题（根因同源）

`market_actor::spawn_with_store` 在守护进程重启后，从 SQLite 恢复内存业务对象时只用了
**少量扁平列**重建。列里没有的丰富字段全部退化为默认值：

- **W-04 任务规格**：`StoredTask` 只有 10 个扁平列。`restore_tasks_from_store` 重建
  `TaskSpec` 时 `context` 被清空、`todo` 退化为 `"(restored from disk)"`、`done`/`trace`/
  `required_skills` 全丢 —— 一次重启后，任务的执行上下文、已办/待办轨迹、技能要求都不可用。
- **W-05 智能体卡片**：`StoredAgent` 只有 6 个扁平列。恢复出的卡片 `version` 恒为
  `"0.0.0-restored"`，`description`/`modalities`/`models`/`endpoint`/`pricing`/`sla`/
  `total_calls`/`success_rate`/`evidence_grade`/`verified` 全部退化为默认值 —— 卡片的能力
  声明与定价/SLA 在重启后失真。

## 二、修复

| 项 | 改动 |
|---|---|
| `storage/persist.rs` | `tasks` 表加 `spec_json TEXT`、`agents` 表加 `card_json TEXT`；`StoredTask`/`StoredAgent` 各加一个 `Option<String>` 字段；`upsert_*`/`load_*` 全列读写；新增幂等迁移 `migrate_add_text_column`（`PRAGMA table_info` 探测，新库旧库都安全） |
| `marketplace/mod.rs` | 快照写完整 `TaskSpec`/`MarketAgentCard` 规范 JSON；恢复**优先反序列化完整对象**，再用扁平权威列覆盖 |
| `tests/v274_test.rs` | 两条恢复测试携带丰富 JSON 并断言字段存活（端到端覆盖生产恢复路径） |

**权威列优先级（关键设计）**：恢复时不是盲目信任 JSON 副本——

- 任务：`budget`/`winner_price`/`deadline`/`state`/`owner`/`goal`/`requester`/`created_at`
  与单独解析的 `verification_policy` 一律以**扁平权威列**覆盖；丰富轨迹字段（context/done/
  todo/trace/required_skills）以 JSON 为准。
- 卡片：`stake`/`reputation_score`/`created_at` 以**扁平权威列**覆盖（资金/信誉不允许被 JSON
  改写），`updated_at` 取 max；丰富声明字段（version/pricing/sla/modalities/models 等）以
  JSON 为准；JSON 内 skills 为空时用扁平 `skills` 列兜底。

**不 panic 的降级**：完整 JSON 缺失（v3.5.4 之前的遗留库）或损坏时，回退旧的安全默认构造并
显式 `eprintln!` 告警（带 agent/task id 与错误），经济字段仍由扁平权威列恢复，不影响账本与结算。

## 五、诚实边界

- 本版只解决"重启后内存重建丢字段"，**不改动** v2.8.4 已有的证据闸门、v3.5.1 的账本哈希链
  与资金守恒/独立审计机制。
- `card_json`/`spec_json` 不是可信资金来源：资金、信誉、生命周期状态一律以扁平权威列为准；
  JSON 只承载扁平列未覆盖的丰富声明与轨迹。
- 能整份重写 SQLite 数据库文件（含锚定 head）的攻击者仍不在 tamper-evident 威胁模型内——
  该边界与账本哈希链一致，已在既有文档中说明。
