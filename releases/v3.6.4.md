# v3.6.4 — 修复 v3.6.3 gnu 资产缺失：改用 cargo-zigbuild 定位 glibc 2.35（不再依赖退役的 ubuntu-22.04 runner）

v3.6.4 是 v3.6.3 之后的**补丁版本（patch）**，只修复发布流水线，**不含任何运行时代码改动**
（Rust/SDK/前端源码相对 v3.6.3 无功能差异，仅版本号与 CI/文档）。

## 一、根因（不是代码问题）

v3.6.3 的 Release 流水线中，musl / macOS / Windows / Python SDK 全部成功，但
`Build x86_64-unknown-linux-gnu` 等满 15 分钟后失败。失败注释为：

> The job was not acquired by Runner of type hosted even after multiple attempts.

即 v3.6.3 为把 gnu 基线降到 glibc 2.35 而把该 job 钉到的 **`ubuntu-22.04` hosted runner 已处于
退役状态、无法分配**（GitHub 同期正把 `ubuntu-latest` 迁移到 Ubuntu 26，老镜像容量在收缩）。
这与代码、依赖、测试无关：PR #30 跑在 `ubuntu-latest` 上的 `Rust - ubuntu-latest` 检查是通过的。

结果：v3.6.3 Release 已创建并含 **13 个资产**（musl 三件、mac 三件、Windows 三件、Python 两件、
旧命名 tar.gz 两件），npm `@twinsearth/agent-universe@3.6.3` 已发布且 dist-tag latest=3.6.3，
**唯独缺少 gnu 三件**（`gsn-daemon-x86_64-unknown-linux-gnu(+.sha256/.tar.gz)`）。

## 二、修复：在 ubuntu-latest 上用 cargo-zigbuild 以 glibc 2.35 为目标

不再依赖任何特定老版本 hosted runner，改为在当前受支持的 `ubuntu-latest` 上用 Zig 工具链
交叉定位 glibc 版本（业界在老 runner 退役后的标准做法，结果可重复）：

- gnu job 的 `runs-on` 从 `ubuntu-22.04` 改回 `ubuntu-latest`。
- 新增 step 安装 `cargo-zigbuild` 与 `ziglang`（用户级 pip，无 sudo）。
- 构建命令：`cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.35 --bin gsn-daemon`。
  产物**仍是动态链接、glibc 依赖 ≤ 2.35 的 gnu 二进制**，输出路径仍是标准
  `target/x86_64-unknown-linux-gnu/`，后续打包/原始二进制/sha256/上传步骤完全不变。
- musl / macOS / Windows 三个目标**保持 v3.6.3 已验证成功的原构建路径**，本版不改动，回归面最小。

zigbuild 通过 `zig cc` 接管 C/汇编（含 ring），不依赖目标机 glibc 头文件，因此「以哪个 glibc
为目标」只由三元组后缀 `.2.35` 决定，与 runner 自身 glibc 版本解耦。

## 三、验证

- 工作流 YAML 解析通过，矩阵仍为 4 目标；gnu 与其余三个目标的构建步骤按 `if` 正确互斥。
- 无 Rust 代码改动，本地全量关卡结论同 v3.6.3（0 failed、clippy/fmt/no-panics/unsafe 干净、
  版本一致性通过、metadata --locked exit 0）。
- **待发布后实测**：下载 v3.6.4 的 gnu 二进制在本机（glibc 2.35）直接运行，确认不再报
  `GLIBC_2.39 not found`；`file`/`ldd` 复核其动态链接且 glibc 需求 ≤ 2.35。

## 四、对用户的影响

- 老 glibc（Ubuntu 22.04 / Debian 12 等）用户：v3.6.3 请先用 musl 静态资产或 npm；升级到
  **v3.6.4** 后 gnu 二进制恢复可用。
- 更新器：v3.6.4 起 gnu/musl 两类 Linux 资产齐备，`platform_asset_name` 按自身编译时 libc
  选择的逻辑（v3.6.3 引入）在本版才首次对 gnu 用户真正可用。
- 默认 minor 通道只跟 `x.Y.0`，不会自动跳到 3.6.4；补丁通道或手动 `gsn update 3.6.4` 获取。

## 五、诚实边界

- 未恢复使用 `ubuntu-22.04` 镜像（它仍可能不可分配）；glibc 基线保障改由工具链而非 runner 提供。
- gnu 目标仍为 `x86_64`；aarch64 gnu/musl 不在发布矩阵。
- v3.6.3 Release 的 gnu 缺口不做回填式改写；以 v3.6.4 完整发布为准（符合「不覆盖/重打已发布
  tag」的发布纪律）。
