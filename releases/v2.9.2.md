# v2.9.2 — CI 工程化：Windows 矩阵接入、静态关卡（panic/unsafe）接入 CI

本版是 v2.9.1 的工程化收尾：把 v2.9.1 临时推迟的两项 CI 能力正式落地——**Windows 矩阵**与
**静态关卡 static-gates**，并把两个本地就绪但未提交的检查脚本正式入库。核心原则仍是
**「文档里写了但没人执行的规则，必须变成会红的检查。」**

## 一、Windows 矩阵接入（rust-test）

rust-test 矩阵由 `[ubuntu-latest, macos-latest]` 扩为
`[ubuntu-latest, macos-latest, windows-latest]`，在 Windows 上跑完整链条：

- `cargo fmt --check`、`cargo build`、`cargo test`、`cargo clippy --all-targets -- -D warnings`、
  `gsn-daemon --help`。
- 此前 Windows 专属代码（`sandbox/runtime/winjob.rs` 的 Job Object、`process.rs` Windows 分支、
  `#[cfg(windows)]` 路径）**没有任何 CI 覆盖**，只能靠本地 Windows 机器偶发验证；现在每个 PR
  都会被编译和测试。

## 二、静态关卡接入 CI（static-gates job）

新增 `static-gates` job（ubuntu，Node 20），跑两个机械检查：

| 检查 | 脚本 | 作用 |
|---|---|---|
| No panic paths | `scripts/check-no-panics.mjs` | 先剥离注释/字符串/char、移除 `#[cfg(test)]`，再匹配 `.unwrap()`/`.expect()`/`panic!`/`unreachable!`/`todo!`/`unimplemented!`（**不匹配** `assert!`）；生产代码命中即红灯。 |
| Unsafe containment | `scripts/check-unsafe-containment.mjs` | 每个 `unsafe` 项必须收容在平台模块、且有对应 `// SAFETY:` 理由；SAFETY 数少于 unsafe 数即红灯。 |

**为什么要先剥离注释/字符串**：朴素 grep 会把模块文档里引用的上游 `.unwrap()` 也计入
（在本项目第一次扫描时报 312 处，收紧后真实生产命中为 0）。剥离后才能得到可信结果。

## 三、检查脚本正式入库

- `scripts/check-no-panics.mjs`、`scripts/check-unsafe-containment.mjs`：v2.9.1 时已在本地
  验证通过（TOTAL=0、winjob 3 unsafe/3 SAFETY），但当版未提交（untracked）；本版正式入库并
  接入 CI，此后 panic 回退或无理由 unsafe 都会立即变红。

## 验证

- Linux 本地全量 `cargo test`：**全部通过、0 failed / 0 ignored**（172 lib + 各集成测试）。
- `cargo clippy --all-targets -- -D warnings`：**零警告**；`cargo fmt --check`：干净。
- `node scripts/check-no-panics.mjs`：TOTAL production panic sites = **0**。
- `node scripts/check-unsafe-containment.mjs`：仅 winjob.rs 3 unsafe / 3 SAFETY，**通过**。
- Windows 与 macOS 行为由 CI 矩阵验证（本地为 Linux，无法直接覆盖）。

## 边界说明（不夸大）

- 静态关卡在 ubuntu 上跑，但扫描的是 `gsn-core/src` 全量源码（含 Windows 门控代码），
  因此能覆盖所有平台的 panic/unsafe，而不只是 Linux 代码。
- 机械检查是「兜底闸门」，不替代语义测试：它能拦住新增 panic 路径与无理由 unsafe，
  但不能证明逻辑正确。
- 已知未修项（沿用 v2.9.1 文档，不在本版范围）：node.rs/api.rs 仍有 8 处
  `let _ = node.persist();` 丢弃持久化错误；结算仍按托管总额付款而非中标价。
