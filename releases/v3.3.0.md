# v3.3.0 — 业务化 chain-anchor：离线锚定构造与双校验（anchor/verify）

v3.3.0 是 v3.2.3 之后的**中版本**。按版本语义，中版本以**新插件功能**交付、不改内核。
本版只做一件事：**把第 8 个官方插件 `chain-anchor`（链上锚定）从"通用 exec 承载"
业务化为随插件承载真实算法的 `anchor` / `verify` entry**，离线移植自
`contracts/src/AgentCardAnchor.sol`。

## 一、要解决的问题（根因）

v3.2.3 业务化 agent-skill 后，9 个官方插件中仅剩 **2 个**（chain-anchor / chain-bridge）
是通用 exec 承载。但 v3.2.3 的探查结论是"chain-anchor 在单体 Rust 中无独立算法"
（`chain/mod.rs` 仅 re-export PoCV），因此当时未业务化。

进一步探查发现：**chain-anchor 的真实算法不在 Rust 单体里，而在真实的 Solidity 合约
`contracts/src/AgentCardAnchor.sol`（71 行）中**——它定义了锚定记录结构、授权锚定者
闸门、不可变首写与双校验 verify。这是真实、独立、输入输出明确的算法，**应当**被
插件承载，而不是让"链上锚定"插件只跑通用 exec。

> 本项目批评上游的核心模式之一是「没有调用点的修复不算修复」：一个声称"链上锚定"的
> 插件，若没有真实的 `anchor` / `verify` 方法，就没有兑现能力。

## 二、技术闸门：纯 Python keccak256

合约的锚定键是 **keccak256**（Ethereum），不是 NIST SHA3-256：

- `cidHash = keccak256(cid)`、`agentDidHash = keccak256(agent_did)`；
- Rust 端仅有 `sha2`，无 keccak/eth/alloy 依赖；标准库 `hashlib.sha3_256` 是 NIST
  SHA3（padding `0x06`），而 Ethereum keccak256 的 padding 是 `0x01`——两者对同一
  输入给出**不同**结果（空串：keccak `c5d246…` vs SHA3 `a7ffc6…`）。

故在 entry 内**纯 Python 实现 keccak256**（Keccak-f[1600] 24 轮 permutation +
sponge，rate=136、capacity=64、domain byte `0x01`）。

### 调试闭环（根因 → 修复 → 验证）

首版实现的 keccak 输出与权威值不符，按 sponge padding 与 permutation 分段二分：

- 把 padding 换成 NIST 的 `0x06` 跑自己的 permutation，仍对不上标准库 SHA3，
  证明 bug **在 permutation 内部**而非 padding；
- 分步 dump 确认初始状态、theta、rho/pi（双射 25 目标位全覆盖）、chi 均正确；
- **根因**：硬编码的 24 个轮常数（RC）表**从 RC[2] 起约 12 个抄错**（典型：RC[2]
  误写 `…808b`/应 `…808a`、RC[3] `…8081`/应 `…8000`、RC[15] `…0080`/应 `…8003`、
  RC[23] `…8082`/应 `…8008`）。以 pycryptodome 源码 `src/keccak.c:275-300` 的权威
  `roundconstants` 替换后，全部用例通过。

权威向量（均已匹配）：

- `keccak256("") = c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`
- `keccak256("abc") = 4e03657aea45a94fc7d47ba826c8d667c0d1e6e33a64a036ec44f58fa12d6c45`
- 已验证长度：0、15（DID）、135、136、137（rate 边界）、200、256、272。

## 三、业务化：ANCHOR entry（plugin/official/mod.rs）

新增 `ANCHOR_ENTRY`（Python，内嵌 keccak256），并在 `official_entry_source` 中把
`OFF_CHAIN_ANCHOR` 映射到该 entry。spawn 时 entry 写入隔离工作目录，call 时在隔离进程
`import plugin` 并调用业务方法——与 v3.1.0 起其它业务插件完全一致。

entry 暴露 6 个方法：

| 方法 | 作用 |
|---|---|
| `status` | 返回插件 id、tier、方法清单 |
| `anchor` | 离线移植合约 `anchor()`，写入锚定记录 |
| `verify` | 离线移植合约 `verify()`，双校验 |
| `get_anchor` | 返回某 cidHash 的完整锚定记录 |
| `add_anchorer` | owner 添加授权锚定者 |
| `remove_anchorer` | owner 移除授权锚定者 |

## 四、规则移植（与合约逐分支对齐）

`anchor` 闸门（严格对齐 `AgentCardAnchor.sol:47-50`）：

1. `cid` 非空，否则 `empty cid`；
2. `agent_did` 非空，否则 `empty did`；
3. `anchorer` 必须在 `authorized_anchorers` 中，否则 `not authorized anchorer`；
4. `cidHash` 不在 `anchors` 中（**首写后不可变**），否则
   `anchor already exists; immutable`；
5. 通过则写记录 `{cidHash, agentDidHash, anchoredAt, anchorer}`。

`verify` 双校验（对齐合约 `:65`）：

- `valid = 锚定记录存在 && anchoredAt > 0 && agentDidHash == keccak256(agent_did)`。

授权管理（对齐合约 `addAnchorer`/`removeAnchorer`）：仅 `actor == owner` 可增删
授权锚定者，否则 `not owner`。

### 离线诚实边界

- 离线插件**不做真实 RPC、不读 `block.timestamp`**，不声称记录已真实上链；
  `anchoredAt` 由调用方传入**单调时间戳**（不传=0，verify 因此判 invalid）；
- 与其它业务插件一致：插件无跨调用内存状态，`anchors` 与 `authorized_anchorers`
  经 payload 传入，写方法返回更新后状态由调用方持有。

## 五、测试

### process.rs（新增 3 个隔离测试，在隔离进程中真实加载 entry 并调用）

- `chain_anchor_then_verify_via_entry`：owner 锚定成功，正确 cid+did 的 verify 通过；
- `chain_anchor_duplicate_is_immutable_and_wrong_did_fails`：重复 anchor 同一 cid 被拒
  （不可变），错误 DID 的 verify 失败；
- `chain_anchor_unauthorized_and_empty_rejected`：未授权锚定者、空 cid、空 did 均被拒。

`chain-bridge` 的 `is_none()`。

## 八、已知边界

- 9 个官方插件中仅剩 **1 个**（chain-bridge）为通用 exec 承载。它对应
  `ReputationRegistry.sol` / `PoCVSettlement.sol`（跨链信誉桥接），算法更复杂，
  需先读完这两个合约再业务化，不能凭空编造。
- 本版锚定为**离线**构造：不声称真实上链、`anchoredAt` 为调用方传入；真实链上
  写入/读取需补 RPC 后端（后续）。
- 已知未修项（沿用）：PMB 消息签名为对称 HMAC（跨节点非对称签名待后续）、部分
  `let _ = node.persist()` 丢弃持久化错误、结算按托管总额付款而非中标价、API token 无法
  表达标准 DID、Unix/macOS 进程后端部分边界无强制原语（需 waiver）。
