# v3.6.3 — 更新器代理支持 + Linux 老 glibc 兼容（gnu 降基线 / 新增 musl 静态）+ 带外恢复

v3.6.3 是 v3.6.2 之后的**补丁版本（patch）**，只解决 v3.6.2 汇报末尾登记的两条部署诚实边界，
外加一条存量恢复便利工具。不改动任何资金 / 共识 / 持久化 / 通道策略语义。

1. GitHub 官方 Linux 二进制由 CI（Ubuntu 24.04，glibc 2.39）构建，老 glibc 主机直接运行报
   `GLIBC_2.39 not found`。
2. 更新器不读 `HTTPS_PROXY`，企业/沙箱网络下无法经正向代理取 registry 与 Release 资产。
3. 存量 v3.6.1 节点更新器无法自愈，缺少一键带外恢复手段。

## 一、修复 1：Linux 老 glibc 兼容（gnu 降基线 + musl 静态）

`.github/workflows/release.yml`：

- gnu 目标的 runner 从 `ubuntu-latest`（24.04 / glibc 2.39）**钉到 `ubuntu-22.04`（glibc 2.35）**。
  官方 `gsn-daemon-x86_64-unknown-linux-gnu` 自此可在 Ubuntu 22.04 / Debian 12 等仍在广泛使用的
  老 glibc 发行版上直接运行。
- **新增 musl 静态目标** `x86_64-unknown-linux-musl`（runner 装 `musl-tools`，linker 走 `musl-gcc`），
  额外产出 `gsn-daemon-x86_64-unknown-linux-musl(+.sha256/.tar.gz)`。该二进制无 glibc 依赖，
  覆盖 Alpine / 无 glibc 环境，以及想要单一静态可执行文件的用户。

`gsn-core/src/update/registry.rs::platform_asset_name`：Linux x86_64 按**更新器自身编译时 libc**
（`cfg!(target_env = "musl")`）选择 gnu 或 musl 资产，而非运行时探测——gnu/musl ABI 不可混用。

> 诚实边界：本机云 VM 无 sudo/apt、无 `musl-gcc`，musl 静态构建**不由本地验证**，由发布流水线
> （ubuntu-latest + musl-tools）构建产出后，下载资产用 `file`/`ldd` 与实际运行复核。gnu 降到
> ubuntu-22.04 后的「本机 glibc 2.35 可直接运行」同样以发布后下载实测为准。

## 二、修复 2：更新器支持 HTTPS_PROXY（CONNECT 隧道）

`gsn-core/src/update/https.rs` 新增：

- 读取 `HTTPS_PROXY`/`https_proxy`（退而求其次 `HTTP_PROXY`/`http_proxy`）；命中
  `NO_PROXY`/`no_proxy` 则直连。NO_PROXY 支持精确主机、域后缀、前导 `.`、`*.domain` 与 `*`。
- 仅支持 **http 正向代理承载 `CONNECT` 隧道**（企业网络最常见形态）：建立到目标的隧道后，TLS
  仍在隧道内**端到端**进行（rustls），代理只见 SNI/目标主机名，看不到明文。
- 支持 `user:pass` 代理认证（`Proxy-Authorization: Basic`），Base64 手写实现、不引新依赖。
- **非法配置显式报错而非静默直连**：`https://` 形态代理、缺端口、空主机、非 ASCII 凭据都返回
  类型化错误，避免在用户以为走代理时被悄悄绕过；CONNECT 非 2xx 拒绝，407 单独提示。
- CONNECT 响应读到 `\r\n\r\n` 即止，不吞掉隧道建立后的 TLS 字节。

新增 4 组纯函数单测（base64 RFC4648 向量、代理解析与非法形态、NO_PROXY `*.domain` 规则、
CONNECT 200/407/502 解析）。开发中即抓到一个真实规则缺陷：初版未处理环境里大量存在的
`*.npmjs.org` 形态，已修正并加回归。

**真实联网验证（本机）**：
- 直连路径：`registry.npmjs.org` 在 NO_PROXY，`gsn version --check` 成功。
- 代理路径：本进程清空 `NO_PROXY` 强制走环境中的正向代理，经 **CONNECT 隧道端到端**成功拉取
  npm packument 并正确判定版本（代理凭据全程不打印、不落盘）。

## 三、修复 3：存量带外恢复脚本

新增 `scripts/recover-update.sh`（POSIX sh）。面向无法靠自动更新自愈的存量节点（典型 v3.6.1）：

- 默认走**二进制**方式：按平台下载对应原始二进制 → 校验随附 `.sha256`（不符绝不覆盖）→
  备份旧文件 → 同文件系统原子替换。
- `--npm` 走 `npm install -g @twinsearth/agent-universe@<ver>`；`--version` 可指定目标
  （脚本内置默认恢复目标 3.6.3）；`--dest` 指定安装路径。
- 覆盖 Linux x86_64 / macOS arm64 二进制恢复；其余平台提示改走 npm。尊重 `HTTPS_PROXY`（curl）。

## 四、验证

- `cargo test`：全量 **0 failed**（update 模块由 v3.6.2 的 25 增至 **29**，净增 4 个代理相关测试）。
- `cargo clippy --all-targets -D warnings`：0 warning；`cargo fmt`：通过。
- 静态关卡：生产代码裸 panic **0**；`unsafe` 全部带 SAFETY（3/3）。
- 版本一致性：`scripts/check-version.sh` 通过（3.6.3 ↔ gsn-core 0.3.63，全声明点一致）；
  `cargo metadata --locked` 通过。
- 真实联网：直连 + 强制代理 CONNECT 两条路径均成功（见第二节）。
- musl 静态构建、gnu 降基线后的老 glibc 实跑：**待发布流水线产出后下载实测**（本地无 musl-gcc）。

## 五、存量 v3.6.1 / v3.6.2 节点如何到 3.6.3

- v3.6.2 起更新器已能联网：默认 minor 通道只跟 `x.Y.0` 基线、不会自动追补丁；要到 3.6.3 用
  `gsn update 3.6.3` 手动更新，或 `GSN_UPDATE_TRACK=patch gsn update`（白名单/贡献者 patch 通道）。
- v3.6.1 无法自愈：`sh scripts/recover-update.sh`，或
  `npm install -g --no-fund --no-audit @twinsearth/agent-universe@3.6.3`。
- 老 glibc 主机若使用 gnu 二进制，请到 3.6.3 Release 下载（基线已降）；Alpine/无 glibc 用 musl 资产。

## 六、仍存在的诚实边界

- 不支持把 `https://` 代理（到代理本身先 TLS）作为本版目标；遇到显式报错（极少见部署形态）。
- musl 仅覆盖 `x86_64`；aarch64 musl、其他架构不在本版发布矩阵。
- 自动更新仍不跨大版本自动升级（更高 major 只提示手动），这是刻意的安全策略而非缺陷。
