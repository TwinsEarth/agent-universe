# v2.8.7 — Agent Sandbox 认证/所有权/资源限制/随机 id/孤儿清扫

对应《v2.8.2 增量审计 / Gap Analysis》**§3.3（Agent Sandbox 三个 critical + 五个 high）**。
v2.7.6–v2.8.0 引入的沙箱子系统（约 1,847 行），其安全边界此前**只存在于文档与单元测试中**：

| 严重度 | 审计发现 | 证据（v2.8.2） |
|---|---|---|
| critical | 未认证远程代码执行：`POST /api/v1/sandboxes/{id}/exec` 接受任意 Python/JS，REST 路径无认证，监听 `0.0.0.0:4002`，无所有权模型 | `node.rs:1069-1105`、`sandbox/api.rs:144-182` |
| high | `NetworkGuard::check_egress` / `PermissionChecker::check` / `AuditLog::append` / `ExecutionToken::authorize` 生产调用点为零 | `sandbox/security.rs:55-78,188` |
| high | 六项资源限制仅两项生效；stdout/stderr 用无上限 `read_to_end` → 父进程内存 DoS | `process.rs:261-276` |
| high | id 是 `sb-N` 计数器，重启后 `sb-1` 被重新发放并继承上一个 `sb-1` 的文件 | `manager.rs:67-70` |
| high | 请求体被解析后直接丢弃（`acquire(None)`），调用方无法设置任何策略 | `api.rs:85-94` |

## 根因

- 认证闸门只覆盖 `/api/v1/mcp`，沙箱 REST 路径完全在认证之外；且沙箱没有 owner 概念，
  任何调用者可 exec / pause / destroy 任意 `sb-N`。
- 安全组件（NetworkGuard / PermissionChecker / AuditLog / ExecutionToken）只在
  `tests/v279_test.rs` 里被调用，生产代码零调用——按审计规则“没有调用点的修复不算修复”。
- 沙箱身份用进程内计数器 `sb-N`，不持久化、不校验目录是否已存在，导致重启后 id 复用、
  跨请求继承文件；计数器 id 也可被顺序猜测。
- 输出读取无上限，恶意 / 失控代码可令守护进程内存无限增长。

## 修复

### 1. 变更类统一认证 + 所有权绑定（critical）

- `handle_api` 在只读放行（list/get）后，对**所有变更类**（create/exec/pause/resume/destroy）
  统一要求非空 `caller`，否则返回 **401**（`{"error":"未认证：变更类沙箱操作需要 Bearer 认证"}`）。
- create 成功后把沙箱**绑定 owner**（`bind_owner`）；exec/pause/resume/destroy 各自先经
  `check_owner(id, caller)`，非所有者返回 **403**。所有者主体由认证令牌派生（见下）。
- 认证主体派生与 REST 同源：`node.rs::extract_caller`（Bearer 令牌 → `sub:<sha256 前 16 hex>`，
  不泄露明文），改为 `pub(crate)` 供 MCP 复用。
  - **sse.rs**：MCP 通过 Bearer 认证后，用 `extract_caller` 派生主体传入沙箱桥；
  - **stdio.rs**：本机受信传输，固定主体 `local:stdio`。
- `SandboxMcpBridge::call` 增加 `caller` 参数，经 `spawn_blocking` 透传到 `handle_api`。

### 2. 随机、不可猜、单路径校验的 id（high）

- `next_id` 改为 `sb-` + 8 随机字节的 16 hex（`rand`），不再是 `sb-N` 计数器；
  生成后经 `Self::validate_sandbox_id` 自检（单一 id 校验函数，拒绝路径分隔符 / `..` / 空）。
- 多个 id 全局唯一、不可顺序猜测，杜绝重启后 `sb-1` 复用与文件继承。

### 3. 输出 / 资源上限真正生效（high）

- `read_bounded` 有界读取 stdout/stderr：超过 **`MAX_OUTPUT_BYTES = 1 MiB`** 即截断，
  防止父进程内存 DoS。
- 请求体配置（env / initial_files / timeout_ms / allowed_domains / resources）经
  `config_from_body` 真正覆盖默认配置并校验：资源 / timeout 为 0 报错，env 支持对象或
  `KEY=VAL` 数组，`allowed_domains` 非空时启用出站白名单，非法即 400。
- **Windows**：新增 `runtime/winjob.rs`（Job Object），强制内存 / 进程数上限与
  整棵进程树 kill（KILL_ON_JOB_CLOSE / ACTIVE_PROCESS / PROCESS_MEMORY）；
  进程以 `taskkill /T /F` 兜底杀树。

### 4. 孤儿清扫（high）

- `SandboxManager::new` 启动即 `sweep_orphan_sandboxes`：清理 data dir 下上一进程残留的
  `au-sandbox-*` 目录，避免孤儿沙箱 / 文件残留与 id 复用。
- 互斥锁改用 `unwrap_or_else(|e| e.into_inner())`，避免锁毒化后每次调用都 panic。

## 边界说明（不夸大）

- 进程级运行时**仍不提供内核级隔离**：Linux 上是 `bash -c` + `ulimit` + `env_clear` +
  独立临时目录，Windows 上是 Job Object；不可用于运行完全不可信的代码。
- `winjob.rs` 仅 `cfg(windows)`，Linux CI 不编译；windows-sys 0.52 的常量 / 字段名
  需在 Windows 端 `cargo build` 实测确认。
- `docker.rs` / `firecracker.rs` 仍为环境探测（PATH / `/dev/kvm`），未实现 Sandbox trait；
  相关 README / 架构文档中的“microVM（Firecracker）”等表述同步诚实化。
