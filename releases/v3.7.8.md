# v3.7.8 — AUSec CPU 调度（2/3）：竞争下确定性配额分配仿真（仿真时钟：敏感先保障、剩余给容忍）

## 一、交付了什么
本版为 AUSEC-DESIGN §3.1 中 v3.7.8 的交付。v3.7.7 的 `arbitrate_priority` 只产出
优先级/组内份额、`capacity` 仅登记不约束；本版新增
`gsn-core/src/ausec/cpu_schedule.rs`，把它推进到"**节点 CPU 已被其他任务占掉一部分、
沙盒之间真实竞争**"时的**确定性配额分配**，并用一个多 tick 的**仿真时钟**可重复地
跑分配过程，同时给出**无优先级 flat 对照**以量化"敏感优先"到底压低了多少敏感任务
损失。全部纯确定性、整数（u64/u128 + 千分点）、零 syscall、零 unsafe、thiserror
无 panic——它是调度策略的**仿真/决策面**，tick 是逻辑步而非墙钟。

1. **两级分配：Sensitive 先保障，剩余给 Tolerant**
   - 每个 tick 先计算 `available = capacity − external_load_millis`（`external_load`
     对应外部参考中"节点 50% CPU 已被其他任务占掉"）；再在**时延敏感组**内按
     "权重 + 需求上限"分配，敏感组**用剩的**容量才给时延容忍组。
   - 极端竞争场景（容量 100、外部占 50、敏感与容忍各需 50）下：priority 策略
     Sensitive 满足率 1000‰（impact 0）、Tolerant 0；无优先级 flat 对照下 Sensitive
     仅拿到 25（impact 500‰）——确定性地证明"敏感先保障"的保护效果。
2. **整数加权配水（weighted water-filling，含需求上限）**
   - 成员最终 `0 <= granted <= demand`；总分配 `= min(capacity, Σdemand)`——**需求不足
     时剩余容量留空，不硬塞**，守恒可单测断言。
   - 被需求 cap 住的成员固定拿满后退出，其权重从后续比例基中剔除（标准 water-filling），
     剩余成员在剩余容量里按权重再分；按权重 floor 后的余数按"权重降 → 位置升"逐个 +1
     补齐，结果对成员排列顺序不敏感、完全确定。全程 u128 中间运算、无浮点。
3. **仿真时钟 + 多 tick 累计**
   - 入参 `ticks:[{external_load_millis, demands?:[{sandbox_id, demand_millis}]}]`；
     等待模型生成（Waiting）的沙盒该 tick **直接不列需求**，granted=0，刻画"约 90%
     沙盒平均 CPU <5%、等待期空转但仍占内存"的稀疏负载。
   - 每 tick 输出每个活跃沙盒在 priority / flat 两策略下的 granted、shortfall、满足率，
     以及 Sensitive/Tolerant 两组汇总；`aggregate` 跨 tick **先求和再算比率**（不是比率
     平均），并累计 external/available。
4. **fail-closed 复用 v3.7.7 信任仲裁**
   - 先调 `arbitrate_priority`（capacity>0、空/重复 id、权重/申请非法、**低信任级自报
     Sensitive 拒绝**、黑名单拒绝）；再逐 tick 校验：`external_load` 超容量、引用不存在
     的沙盒、`demand` 不在 `1..=requested`、同一 tick 重复申报需求——任一非法整体报错
     （全具名 `ScheduleError`），不返回部分结果。
   - PMB 入口 `cpu_schedule_sim` 与 v3.7.7 **共用同一套** capacity/sandboxes 解析
     （重构出 `parse_capacity_and_requests`，tier 缺省仍按 `third_party` 最小信任），
     新增 `parse_ticks`；常量 `METHOD_CPU_SCHEDULE_SIM="cpu_schedule_sim"`、字节桥
     `handle_cpu_schedule_sim`（空负载按 `{}` → 缺字段错误）、单一 register 点注册一行。

- 新增类型：`ScheduleError`（7 变体）、`TickDemand`、`ScheduleTick`、`AllocSummary`、
  `TickEntry`、`TickSchedule`、`AggregateSchedule`、`ScheduleSimulation`，纯函数
  `run_schedule_simulation(capacity, sandboxes, ticks)`；在 `ausec/mod.rs`
  `pub mod cpu_schedule` 并 re-export（不与 v3.7.7 符号冲突）。
- PMB 入参：在 v3.7.7 `capacity_millis` + `sandboxes[]` 基础上加 `ticks[]`；比率字段
  `met_permille/impact_permille` 在无需求（demand=0）时为 `null`（用 `checked_div`，
  绝不除零），而非伪造 1000/0。

## 二、测试（旧实现无法表达的断言，7 新增）
- cpu_schedule.rs 5 个：加权配水守恒与需求 cap（cap 成员固定、其余分剩余、总=min(容量,
  总需求)）、总需求不足时容量留空不硬塞；等权三人争 10 → floor 3/3/3、余数按位置升
  +1 得 4/3/3、总和守恒，权重 3:1 争 8 → 6/2；50% 被占下 Sensitive 全保 50、Tolerant 0、
  flat 对照敏感仅 25（impact 500‰）、priority impact=0 严格优于 flat；一般竞争下
  priority 敏感满足率严格高于 flat 且总分配不超可用 60；Waiting 沙盒不列需求全 0、
  多 tick 累计 available=200、无需求比率为 None；以及无 tick / 外部超容量 / 未知沙盒 /
  需求越界 / 重复需求 / 第三方自报 Sensitive 透传 Cpu 错误的全 fail-closed。
- mod.rs 1 个 PM 桥：经 `cpu_schedule_sim` 入口验证 50% 被占下 priority 敏感 50 全保、
  impact=0、tolerant 0、flat 敏感 25；字节桥 round-trip 可解析、空负载返回错误不 panic；
  无 tick / 外部超容量 / 未知沙盒 / 需求越界全部拒绝。
- `cargo test --lib ausec` **88/0**（较 v3.7.7 的 81 增 7）；全量 gsn-core
  **lib 443 passed / 0 failed**（较 436 增 7）；`cargo fmt --check`、
  `cargo clippy --all-targets -D warnings` 干净（比率用 `checked_div`，无
  manual_checked_ops）；check-no-panics 生产 panic=0；check-unsafe-containment 仍仅
  winjob.rs 3 unsafe/3 SAFETY（本版新增 cpu_schedule.rs **零 unsafe**）；
  `cargo metadata --locked` 通过；npm 3.7.8 ↔ gsn-core 0.3.78。

## 三、诚实边界
- 本版是**仿真**，不是真实执行：**不调用** cgroup cpu.shares/quota、sched_setaffinity、
  时间片抢占或任何 OS 调度原语，**不推进墙钟**，tick 是逻辑步；输出的 granted 不能被
  解读为"内核已按此分配 CPU"。它验证的是**分配策略在竞争下的确定性正确性**，真实限速
  与测量不在本版。
- 外部报道所称"**节点 50% CPU 被占时，时延敏感任务受影响 45.2%→17.3%**"是
  **aiwiki.ai / byteiota.com 对 DeepSeek DSEC 的报道、非本仓复测**；本版仅以"50%
  external_load"作为该场景的**机制动机**，用自己的整数仿真向量证明敏感优先严格优于无
  优先级，**不声称在本仓复现 45.2/17.3 这两个数**。
- flat 对照是"全员按权重共分、忽略时延等级"的反事实基线，用于量化保护幅度；它不代表
  v3.7.7 之前存在某种 flat 实现（v3.7.7 本就不分配容量）。
- 满足率/受影响比例是整数千分点、向下取整；权重 floor 的余数按确定性 tie-break 补，
  调用方不应假设整除，也不应跨 tick 对每 tick 比率取平均（应看 aggregate 求和口径）。
- 信任仲裁仍以"宿主已按插件清单前缀正确裁定 tier"为前提；tier 不由沙盒自填，PMB 入口
  缺省 third_party。突发涌入准入控制与统一 `ausec status`（汇总后端/块/CPU/内存）在
  v3.7.9。
