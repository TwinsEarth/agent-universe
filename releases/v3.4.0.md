# v3.4.0 — 业务化 chain-bridge：跨链信誉桥接与中位数共识（9/9 官方插件全业务化）

v3.4.0 是 v3.3.0 之后的**中版本**。按版本语义，中版本以**新插件功能**交付、不改内核。
本版只做一件事：**把第 9 个、也是最后一个官方插件 `chain-bridge`（跨链信誉桥接）从
"通用 exec 承载"业务化为随插件承载真实算法的 entry**，离线移植自
`contracts/src/ReputationRegistry.sol`。至此，**9 个官方插件全部业务化**。

## 一、要解决的问题（根因）

v3.3.0 业务化 chain-anchor 后，9 个官方插件中仅剩 **1 个**（chain-bridge）是通用 exec
承载。它对应两个已读合约：

- `contracts/src/ReputationRegistry.sol`（207 行，原 ReputationBridge）：**链下信誉的
  链上锚定**，多验证者提交 → 法定人数 → 四维中位数定稿，是 chain-bridge 的真实算法；
- `contracts/src/PoCVSettlement.sol`（172 行）：独立的任务托管/质押/验证投票/结算
  合约，**不是 bridge 核心**，仅作背景。

判定 **chain-bridge 真实算法 = ReputationRegistry**。这是真实、独立、输入输出明确的
算法，应当被插件承载，而不是让"跨链信誉桥接"插件只跑通用 exec。

> 本项目批评上游的核心模式之一是「没有调用点的修复不算修复」：一个声称"跨链信誉桥接"
> 的插件，若没有真实的验证者管理、记录、定稿方法，就没有兑现能力。

## 二、业务化：BRIDGE entry（plugin/official/mod.rs）

新增 `BRIDGE_ENTRY`（Python，内嵌与 chain-anchor 相同的纯 Python keccak256），并在
`official_entry_source` 中把 `OFF_CHAIN_BRIDGE` 映射到该 entry。spawn 时 entry 写入
隔离工作目录，call 时在隔离进程 `import plugin` 并调用业务方法——与 v3.1.0 起其它
业务插件完全一致。

entry 暴露 7 个方法：

| 方法 | 作用 |
|---|---|
| `status` | 返回插件 id、tier、方法清单 |
| `add_verifier` | 离线移植合约 `addVerifier()`，owner 添加验证者（有上限） |
| `remove_verifier` | 离线移植合约 `removeVerifier()`，owner 移除验证者 |
| `record` | 离线移植合约 `recordReputation()`，验证者提交四维信誉 |
| `finalize` | 离线移植合约 `finalize()`，法定人数 + 四维中位数定稿 |
| `get_latest` | 离线移植合约 `getLatestReputation()`，返回最新定稿 |
| `submission_count` | 离线移植合约 `submissionCount()`，返回某 epoch 提交数 |

## 三、规则移植（与合约逐分支对齐）

`add_verifier` 闸门（对齐 `ReputationRegistry.sol`，修复 GAP §9.4 第 1 类）：

1. `actor == owner`，否则 `not owner`（合约是 `onlyOwner`，此前 onlyVerifier 可无限铸
   验证者）；
2. `verifier` 非空，否则 `zero verifier`；
3. 未重复，否则 `already verifier`；
4. `verifier_count < MAX_VERIFIERS(32)`，否则 `verifier cap reached`。

`record` 闸门（对齐合约，修复 GAP §9.4 第 2 类）：

1. `verifier` 必须在验证者集合中，否则 `not verifier`；
2. 四维（quality / speed / honesty / availability）都必须 `0 <= v <= MAX_BPS(10000)`
   （与链下 0–10000 bps 量纲一致），否则 `score out of bps range`；
3. 同验证者对同 (agent, epoch) 重复提交：内容完全相同 = **幂等 no-op**（返回
   `idempotent: true`）；内容不同 = `conflicting resubmission`。

`finalize` 共识（对齐合约，修复 GAP §9.4 第 3 类）：

1. 该 epoch 有提交，否则 `no submissions`；
2. 未定稿，否则 `already finalized`；
3. 存在验证者（`required_quorum = verifier_count/2 + 1`），否则 `no verifiers`；
4. `submitters.length >= quorum`，否则 `quorum not reached`；
5. 对四维各收集提交者分数、取**中位数**（`_median`，插入排序），写
   `ReputationSnapshot`（`finalizedAt` 由调用方传入），记录 agent 的 epoch 列表。

`get_latest`：返回该 agent 最新 epoch（agent_epochs 末位）的定稿；对未知 DID 返回
**全零快照（不报错）**，对齐合约 `getLatestReputation`。

中位数实现对齐合约：插入排序（Python 中下标 `j` 可为 -1，不产生合约 Solidity 中
`uint256(-1)+1` 的溢出问题），返回 `vals[len(vals)//2]`。

### 离线诚实边界

- 离线插件**不做真实 RPC、不读 `block.timestamp`**，不声称记录已真实跨链/上链；
  `finalizedAt` 由调用方传入（与 chain-anchor 一致）；
- 离线用字符串 `agentDidHash + ":" + epoch` 作 epoch key（合约是 keccak(agent, epoch)，
  离线无需再哈希一次）；验证者用 DID/ID 字符串而非合约 address；
- 与其它业务插件一致：插件无跨调用内存状态，`verifiers` / `epochs` / `agent_epochs`
  / `final_snapshots` 经 payload 传入，写方法返回更新后状态由调用方持有。

## 四、原型验证（嵌入前）

- 原型 `bridge_proto.py` 经 `test_bridge.py` 全量 **PASS**（约 28 项断言）：非 owner
  拒绝、增删验证者、零/重复/上限、非验证者/越界记录、单提交法定人数不足、幂等/冲突、
  四维中位数、未知 DID 零快照。
- 首次跑原型出现 2 个失败（submission count=2、idempotent），**根因是测试脚本自身的
  状态传递 bug**：v1 提交后未 `state = carry(result)`，导致 v2/v3 基于丢失 v1 的状态
  提交。修复测试脚本后全部 PASS（插件代码本身无问题）。
